# ADR 0007：Gate 延迟预算按部署类型区分，远程网关改为延后一步生效

日期：2026-09-27

状态：已采纳

## 背景

原设计让 Gate 在热路径上同步运行，300 ms 硬超时。内部试用的隔离烟测中，Gate 在 302 ms 超时降级，没有产出有效标签。

2026-09-27 用生产 Gate 提示词和 20 张卡片，对指定网关顺序发出 20 次请求（`tests/gate_latency_baseline.py`）：

| 模型 | P50 | P95 | ≤300 ms | ≤1,500 ms | JSON 可解析 |
| --- | --- | --- | --- | --- | --- |
| gemini-3.8-flash-high（响应报告为 gemini-3.8-flash，平均推理 150 token） | 6,452 ms | 13,604 ms | 0/20 | 0/20 | 20/20 |
| gemini-3.1-flash-lite | 3,293 ms | 7,358 ms | 0/20 | 0/20 | 20/20 |

把预算放宽到 1–1.5 秒，对这个网关同样无效；如果放宽到 P95，每个决策点要多等 7–14 秒。

代码审查还发现一个问题：超时降级的 trace 记为 `called: true, decision: "fallback"`，而训练样本查询只检查 `called = 1`，超时样本会混入 Gate 训练标签。

## 决定

1. `automation.gate_mode` 默认为 `auto`。模型地址是本机（127.0.0.1/localhost/::1）时，Gate 同步运行，预算仍为 300 ms 硬上限。远程地址则采用 `deferred`：Gate 与上游请求并行，结果留给**同一会话的下一步**使用。它的超时是 `gate_deferred_timeout_ms`（默认 20 s），不阻塞请求。
2. 延后模式下，结果到达前的决策点沿用原来超时降级时的保守策略（情境召回、阈值 +0.1），trace 记为 `fallback/deferred_pending`，因此只有延迟变化，召回行为不变。未消费的结果 10 分钟后丢弃。
3. **降级样本不计入 Gate 标签。** 训练样本只接受 `gate.decision` 为布尔值的步骤；延后生效的样本使用**做出决定那一步**（`source_step`）的特征。本条由单元测试保护，并写入评测规则。
4. 评估 Gate 成本时，以"决策点频率 × 每点增加的延迟"为准，不看单次延迟。延后模式不增加热路径延迟，增加的只有引擎调用费用，受每日调用上限约束。
5. 更换 Gate 模型或网关前，先用 `tests/gate_latency_baseline.py` 测 P50/P95，再定预算。

## 后果

远程 Gate 从此能产出真实标签，代价是决定晚一步生效。如果任务在第一步就需要记忆，靠的仍是触发器和保守召回。是否值得为此部署本地模型，要等真实 Gate 标签积累后再判断，本 ADR 不预设结论。

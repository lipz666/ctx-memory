# ccx M1：工具输出分级（2026-10-03）

设计见 [ccx-design.md](ccx-design.md) 第 6、7 节。M1 只做工具输出这一块，窗口和状态卡留到 M2。

## 1. 做了什么

`ccx serve --mode on`（默认仍是 `shadow`）。

| 部分 | 行为 |
|---|---|
| 分级（`tiers.rs`） | **热**：最新一步的工具输出，不超过 `--hot-cap`（默认 2,500）时保留原文，超过则截取摘录。**温**：更早的输出，超过 `--warm-cap`（默认 400）时换成摘要。同一份输出后面又出现时，前面那次只留一行指引。Chat、Anthropic、Responses 三种协议都支持；输出里有图片等非文本内容时不改动 |
| 摘录 / 摘要（`digest.rs`） | 纯规则，确定性的：开头 60%、中间的报错类行 15%、结尾 25%，省略处标明省略了多少行。只有几行但很长的文本按字符截断。同样的输入永远得到同样的字节，不会破坏提示缓存 |
| 存档（`objects.rs`） | 被缩短的输出原文按内容哈希存在 `CCX_HOME/objects/xNNNNNNNNNNNN`，文件权限 0600 |
| `ccx_expand`（`expand.rs`） | 只对不走流式的 Chat 请求，并且请求本身带了 tools 时才提供。模型可以按 id 用 `query`（返回匹配的行）或 `offset`/`lines`（分页）读回原文。ccx 自己执行这个调用，再和上游多走一轮，Agent 看不到；如果模型同时调用了 Agent 的工具，那次调用先丢掉，读完后由模型重新发起。最多 3 轮，最后一轮不再提供这个工具 |
| 钉住（v2） | 同一个会话里用 `ccx_expand` 读回过的内容，此后附在那份输出的摘要后面（每份输出最多约 1,500 token，保存在 ccx 内存里，重启后清空），避免反复读回。报错类关键词新增 crit / fatal / panic / oom / killed / exited / abort |
| key 保护 | `--upstream-key-stdin`：key 从 stdin 读入，只存在内存里，由 ccx 加到请求头上；客户端只拿一个假 key。请求体里如果出现 key，转发前替换成 `[REDACTED]` |
| 记录 | `steps.jsonl` 里新增 `est_sent`（实际发出去的构成）、`ccx`（各级缩短了多少条）、`expand_rounds` / `expand_calls`；多轮请求的 usage 合计记录。`ccx report` 同时给出改写前的估算，方便对比 |

测试：ccx 19 个单元测试，clippy 无警告。另外用本地假模型做了一次端到端测试：5.7K 的输出被缩短为 1.5K；模型同时调用了 `ccx_expand` 和 `python`，拿到匹配的报错行之后只返回了 `python`，Agent 自始至终没看到 `ccx_expand`。

## 3. 实测（2 个任务，上限 1M）

ABTesting 和 SetConfCrDdl，经过 ccx `on` 模式，用网关上的 gemini-3.8-flash-high。共 60 个请求，0 个错误；输入 873,677（命中缓存 466,545），输出 7,409，推理 10,575。

| 指标 | 值 |
|---|---|
| 单个请求的输入（实测） | p50 14.2K，p95 29.0K，最大 31.9K |
| 同样这些请求改写前（估算） | p50 50.7K，p95 70.8K，最大 72.8K |
| 缩短次数 | 热 4 次，温 769 次（按请求累计） |
| `ccx_expand` | 0 次：模型没有读回过原文 |
| SetConfCrDdl | 54 步，通过，但这个通过无效（见第 4 节） |
| ABTesting | 7 步失败。原因不在 ccx：Agent 用 grep 搜了本仓库的 `bench/` 目录，得到的输出非常大，LOCA 自己的客户端按 128K 上限做裁剪，把除第一条消息外的所有消息都删掉了，任务就此报错结束 |

## 4. 重大问题：LOCA 主分支的成绩无效

LOCA 主分支的工具直接在本机运行，没有沙箱；标准答案目录 `groundtruth_workspace` 就在 Agent 工作目录的上一级。检查轨迹后发现：

- **基线的 8 次通过全都读过评测代码或标准答案**。以 ABTesting 为例，它依次读了任务生成器 `gem/envs/ab_testing_s2l/*.py`、评测脚本 `evaluation/main.py`，以及 `../groundtruth_workspace/expected_ratio.csv`。两次失败都没有这样做。
- M1 实测中 SetConfCrDdl 也一样：有 29 次调用访问了工作目录以外的路径，最后自己运行了评测脚本。
- Agent 还会翻本仓库里之前跑出来的结果（`pilot-8k.log`、其他轨迹文件），以及其他进程的命令行。

结论：**到目前为止 LOCA 的所有成功率（M0 基线 8/10，M1 实测 1/2）都不能用来下结论**。token 和上下文构成的测量仍然有参考价值：它们反映了上下文的形状，只是读源码这类行为让工具输出变得更多。

## 5. 结论与下一步

- M1 的机制已经验收：离线回放动态部分减少 63%；实测中单个请求的输入从约 51K（p50）降到 14K；没有协议错误，Agent 也没有察觉。
- 还没能验收的是成功率（M1 有没有损害任务完成），因为评测环境本身不可信。
- 继续用 LOCA 之前必须改用 **`loca-sandbox` 分支**：工具执行放进 Docker 或 Podman 容器，客户端（也就是调用模型的那一端，ccx 插在这里）和执行工具的服务端分开。本机装了 docker CLI 和 colima，但 colima 目前没有运行。还需要确认沙箱模式下标准答案不在 Agent 能访问的范围内。
- 另一种做法是用自建的小型验收任务：在临时目录里运行，Agent 只能用指定的工具，标准答案不放在本机能读到的位置。规模小、成本可控，也适合按阶段做功能验收。

## 6. 验收（自建验收集）

LOCA 不能用来判断成败，所以 M1 改用自建的封闭验收集来验收，见 [ccx-accept.md](ccx-accept.md)。v2（加了钉住和新的报错类关键词）6 个任务全部通过，输入 token 是基线的 36%，单次请求的峰值从 11.8–22.1K 降到 2.5–5.6K。v1 在 topic_switch 上陷入了反复读回的循环，这正是促成 v2 两处修复的原因。

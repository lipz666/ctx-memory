# ctx-m 设计（草案，2026-10-03）

ctx-m 是 ctx 的重新设计：**写入时把记忆整理成随时可读的状态，读取时只挑选、不现拼；每次注入给代理的记忆不超过约 1,000 token。** 记忆引擎内部可以调用模型（写入和读取都可以），但交给代理的只有这 1k。

## 1. 为什么重做

ctx v0.5 在 BEAM 100K 上是 67.2%（8k 预算 + 简报），见 [guide.md](guide.md) 和 [benchmark-results.md](benchmark-results.md)。问题是：

- **写入存碎片，读取现拼。** 原子事实、片段、档案、话题摘要、用户原话、时间线等十几个通道，简报每题读约 2 万 token。同一个事实出现好几份，计数会数多，"当前值"会选错。错题分类显示，约 18 个百分点丢在"材料有、简报没写对"这一步。
- **靠规则和调参。** 简报规则改了五版以上，功能开关攒了十几个，多数改动的效果在噪声范围内；而且一直在同一批 400 道测试题上调。
- **不能扩展。** 简报靠"全部用户原话"（100K 时约 1.1 万 token），到 1M、10M 会大 10 倍、100 倍。
- **缺少出处结构。** 助手建议的东西和用户自己说的混在一起，只能靠提示词去区分，模型并不照做。

目前公开最好的成绩（BEAM 100K / 1M / 10M）：Exabase 76.9 / 75.0 / 68.0，Hindsight 73.4 / 73.9 / 64.1（检索预算 8,192）。ctx-m 的目标是**用 1k 注入达到同等水平**。

## 2. 原则

1. **1k 是注入给代理的硬上限。** 系统提示不计入。放不下的不给，代理可以按 id 用 `expand` 继续展开。
2. **对话轮次是唯一的真相来源。** 原始轮次不可变；所有派生记忆都指向轮次号，可以随时从轮次重建。
3. **记忆类型少而固定**（第 3 节）：常驻、卡片、事件、情节四层。
4. **每条说法都带结构化出处。** `by`：用户陈述（user）、助手建议（assistant）、用户采纳（adopted）；`status`：当前（current）、被取代（superseded）、有矛盾（contested）。
5. **能用程序算的就不让模型算**：计数、取最新值、日期差、按轮次排序。
6. **固定的模型调用。** 写入每个会话 1 次（必要时 2 次）；读取 0 次或 1 次（第 5 节）。
7. **不积累开关。** 功能在开发集上两遍都超过噪声才保留，否则删掉。

## 3. 数据模型

```
轮次日志（不可变）  #轮次 · 说话人 · 日期 · 原文                    真相来源，只在 expand 时读取
 ├─ 常驻层  长期指令 · 偏好 · 规则                                  每次相关的都带，≤150 token
 ├─ 卡片层  每个主体一张卡：headline · 值（含历史）· 清单 · 事件 · 进展
 └─ 情节层  每个会话一段摘要（保留具体名字、数字、做法）；以后加话题级摘要
```

**卡片（Card）** 是核心。主体可以是一个项目、组件、人、地点或话题线。

```yaml
id: c_marathon_training
title: 马拉松训练
headline: 备战 11 月 3 日的城市马拉松（#12）；周跑量从 40 提到 55 公里（#97）；已买两双跑鞋 Pegasus、Novablast（#30, #71）
values:                       # 键值，同一个键按轮次形成历史链
  - {key: 周跑量, value: 55 公里, turn: 97, by: user, status: current}
  - {key: 周跑量, value: 40 公里, turn: 15, by: user, status: superseded}
items:                        # 清单，每项一条
  - {list: 买的跑鞋, name: Pegasus, turn: 30, by: user}
  - {list: 买的跑鞋, name: Novablast, turn: 71, by: user}
  - {list: 买的跑鞋, name: Clifton, turn: 72, by: assistant}   # 助手推荐，不计入
events:                       # 带日期的事
  - {what: 城市马拉松, date: 2026-11-03, kind: planned, turn: 12, by: user}
notes:                        # 进展：用户做了什么、助手建议了什么、决定了什么
  - {turns: 40-42, text: 用户膝盖外侧疼；助手建议减量一周并加髋外展训练，用户照做}
conflicts:
  - {a: "跑过两次全马（#20）", b: "从没跑过全马（#88）"}
```

- **headline** 由写入时的模型维护，最多约 60 token，是 1k 预算里最主要的内容单元。
- 一张卡超过约 40 条记录就拆成子卡，避免出现 ctx 那种一份档案 268 条、渲染时被截掉的情况。
- 卡片存成 JSON（以后可以导出为可编辑的 Markdown），每次修改都有记录。

## 4. 写入

每个会话一次模型调用（`extract`）：

- **输入**：带轮次号的会话原文（用户消息全文；助手回复保留开头和小标题，有长度上限）、会话日期，以及**相关卡片的当前状态**（标题、headline、现有键、清单名、最近的值）。模型能看到当前状态，才能判断"更新""重复"还是"矛盾"。
- **输出**：对卡片的结构化操作。

| 操作 | 含义 |
|---|---|
| `value` | 设置或更新一个键；与当前值不同时，旧值由程序标为被取代 |
| `item` | 清单加一项，必须带 `by` |
| `event` | 带日期和类型的事（发生、计划、截止……），日期由会话日期换算成绝对日期 |
| `note` | 一段进展（1–2 句，保留具体名字、做法、数字） |
| `conflict` | 用户现在说的与卡片已有的说法不能同时成立，又没说明有变化 |
| `headline` | 被修改的卡片写一条新的 headline |
| `instruction` / `preference` | 常驻层 |
| `session_summary` | 情节层 |

每个操作都要带轮次号，没有的丢弃。程序负责：版本链（同一个键按轮次取最新）、清单去重（名字归一化后相同就合并，并记下提及次数）、卡片合并（新卡标题与已有卡相似度很高时并入）。

## 5. 读取

```
问题 ─▶ 意图判断（规则）─▶ 记录级检索（语义 + 关键词）─▶ 按卡片聚合
     ─▶ 程序计算（计数、最新值、日期差、排序）─▶ 按意图渲染，≤1k
                                              └▶ 可选：compose，一次模型调用，从约 4k 候选写出 ≤1k
```

**意图**：查事实、计数、最新值、时间、排序、总结、是否（矛盾），以及无相关记忆。

**预算（1,000 token）：**

| 部分 | 上限 | 内容 |
|---|---|---|
| 常驻层 | 150 | 与问题相关的长期指令和偏好 |
| 程序算出的结论 | 100 | 计数和各项、最新值和上一个值、两个日期和间隔 |
| 证据 | 650 | 相关卡片的 headline 和匹配到的记录，带轮次和日期 |
| 余量 | 100 | 可展开的卡片 id |

**按意图渲染：**

| 意图 | 渲染 |
|---|---|
| 查事实 | 2–4 张卡片：headline 加匹配到的记录 |
| 计数 | 最匹配的清单：用户陈述和采纳的项（带轮次），单独注明"助手建议、未计入"的项 |
| 最新值 | 键的历史链，按轮次排列，标出当前值 |
| 时间 | 相关事件和两个日期，程序算出间隔 |
| 排序 | 相关进展和事件按轮次排列，每项保留具体名字 |
| 总结 | headline、按轮次排列的进展、会话摘要 |
| 是否 | 有矛盾的两种说法并列，没有矛盾就给相关记录 |
| 无相关记忆 | 不注入，或者一句"记忆中没有关于 X 的信息" |

**两种读取模式**都要测，由开发集结果决定默认用哪个：

- `render`：不调用模型，确定性渲染，延迟最低。
- `compose`：把约 4k 的候选（卡片全文、程序算出的结论）交给模型，写成 ≤1k 的记忆说明。只做选择和压缩，不回答问题。

## 6. 规模

注入的内容来自卡片和摘要，它们都有大小上限；检索的单位是记录，按卡片聚合，规模随主体数量增长，不随轮次数增长。写入时只把与本会话相关的前 K 张卡片交给模型，所以写入成本也不随历史变长。

## 7. 从 ctx 继承和舍弃

- **继承**：Rust 单二进制和基础设施（embed、index、store、session、proxy、MCP、REST）、轮次编号、日期由程序计算、否定句不取代肯定句、长期指令常驻、编码场景的触发器。
- **舍弃**：原子事实加十几个检索通道、2 万 token 的简报、话题摘要（digest）、时间线拼接、各种默认关闭的实验开关。

## 8. 评测纪律

- BEAM 100K：对话 1–10 是**开发集**，可以随便调；对话 11–20 是**测试集**，只在里程碑时跑；500K / 1M 作为留出集。
- 主指标：1k 注入预算下的总分，同时报告平均注入 token 和每个会话的写入 token。
- 改动保留的条件：开发集两遍都超过噪声（总分约 2 个点）。
- 提示词里的例子不能取自任何测评题。

## 9. 原型（`bench/ctxm/`）

先用 Python 写一个最小原型，接入现有的 BEAM 测评脚本（`--systems ctxm-render` / `ctxm-compose`，`--budget 1000`），验证"卡片 + 1k"能不能打平 ctx v0.5 的 8k 成绩。结论成立后再用 Rust 实现。

- `store.py`：轮次、卡片、常驻层、会话摘要；按命名空间存为 JSON。
- `write.py`：每个会话一次 `extract` 调用，把返回的操作应用到卡片上。
- `read.py`：意图判断、记录级检索（向量由一个隔离的 ctx 实例的 `/api/v1/embeddings` 提供，关键词用 BM25）、程序计算、render 和 compose 两种模式。
- 第一阶段只在开发集（对话 1–10）上跑。

## 10. 原型第一轮结果（2026-10-03，BEAM 100K 开发集：对话 1–10，200 题）

答题与评判均为 gemini-3.8-flash-high，BEAM 官方答题提示词和评分。Hindsight 0.10.2 本地部署，提炼模型同为 gemini-3.8-flash-high，设置照搬它在 AMB 中的 BEAM 配置（`bench/adapters/hindsight.py`）。

| 能力 | ctx-m v1 render | ctx-m r2 render | ctx-m compose | Hindsight 1k | Hindsight AMB | ctx v0.5（8k + 简报） |
|---|---|---|---|---|---|---|
| 拒答 | 72.5 | 62.5 | 97.5 | 87.5 | 62.5 | 90.0 |
| 矛盾消解 | 57.5 | 56.9 | 50.6 | 8.1 | 5.6 | 87.5 |
| 事件排序 | 19.1 | 20.1 | 21.6 | 17.6 | 19.0 | 28.8 |
| 信息提取 | 48.3 | 48.8 | 45.4 | 51.7 | 72.1 | 74.2 |
| 指令遵循 | 62.5 | 55.0 | 50.0 | 40.0 | 56.2 | 86.2 |
| 知识更新 | 75.0 | 80.0 | 77.5 | 65.0 | 60.0 | 82.5 |
| 多会话推理 | 30.6 | 19.7 | 19.9 | 28.5 | 37.6 | 25.4 |
| 偏好遵循 | 65.0 | 84.2 | 60.0 | 63.3 | 79.6 | 85.8 |
| 总结 | 37.2 | 33.6 | 35.9 | 23.2 | 47.1 | 46.1 |
| 时间推理 | 38.8 | 53.8 | 30.0 | 43.8 | 40.0 | 70.0 |
| **总分** | **50.65** | **51.44** | **48.85** | **42.88** | **47.97** | **67.65** |
| 平均注入 token | 895 | 948 | 629 | 953 | 19,078 | 6,984 |
| 检索延迟中位数 | 0.16 s | 0.18 s | 11.2 s | 1.5 s | 1.0 s | 11.0 s |

写入成本（同 10 段对话，216 个会话；不含模型的思考 token）：ctx-m 213 次调用，输入 1.19M、输出 0.18M；Hindsight 日志记录到 1,635 次调用，输入至少 6.7M、输出至少 0.51M（另有思考 1.7M），写入墙钟约 83 分钟（10 段并行）；ctx v0.5 输入 3.34M、输出 0.24M。

- 同为约 1k 注入，ctx-m 比 Hindsight 高约 8 个点；Hindsight 用到约 1.9 万 token 也只有 48.0%。这里的 Hindsight 远低于它自报的 73.4%（答题提示词、评判模型、提炼模型都不同），不能当成对它的复现。
- `compose`（读取时一次模型调用）比 `render` 低 1.8：倾向于回答"没有"，没用满预算。默认用 `render`。
- r2（用户原话摘录、事件两两天数、指令放最后）比 v1 高 0.8，在噪声内：时间推理 +15、偏好 +19，拒答 −10、多会话 −11、指令 −7.5。
- 离 ctx v0.5 还差约 16 个点，集中在矛盾消解、指令遵循、时间推理、信息提取。抽查：指令都存了也注入了，但答题模型只给简短答案、不按指令展开；卡片过粗（每段对话 1–4 张，大卡约 175 条记录）。

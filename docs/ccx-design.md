# ccx 设计（草案，2026-10-02）

ccx 是 ctx 的上下文管理分支：**无论对话多长，每次发给模型的上下文都控制在几 K token 以内**。ctx 负责记住，ccx 负责精简；两者先分开开发，以后合并（见第 11 节）。

## 1. 目标与原则

**前提假设**：上下文越长，模型越容易分心、遗漏和自相矛盾（context rot）。所以短上下文的首要目的是让模型更聪明，省钱只是顺带的效果。这一点和 ADR 0004–0007 以成本为目标不同：ccx 的主指标是任务成功率，成本是次要指标。

原则：

1. **按预算构建，而不是超了再删**。每一步都根据完整历史重新生成一份精简视图，而不是在原请求上一点点裁剪。
2. **有损，但可找回**。被拿掉的内容都在本地存档，模型需要时可以用 id 或查询找回。
3. **用户原话神圣**。用户提的要求、约束和偏好只能逐字引用，不改写、不概括；只有用户自己撤回时才移除。
4. **能用规则就不用模型**。工具输出的分级精简全部是确定性的规则；只有折叠成状态卡时才调用模型，而且是异步的。
5. **任何失败都不破坏请求**。出错就退回原请求转发并记录日志，Agent 不会感知到。
6. **不改 Agent**。Agent 本地保留完整历史，ccx 只改它发给模型的那一份。

## 2. 预算口径

| 部分 | 是否计入预算 | 说明 |
|---|---|---|
| 静态前缀：系统提示 + 工具定义 | 不计入，单独统计 | Claude Code、Codex 这一部分通常就有 10–20K，ccx 不改，保证提示缓存命中。瘦身作为 M4 实验 |
| 动态部分：状态卡、找回片段、最近窗口、当前消息 | **计入**，默认 `ccx.budget = 4000` | “几 K”约束的就是这一部分 |

报表里每一步都同时给出“动态 token”和“总输入 token”，避免两种口径混在一起。

## 3. 上下文的形状

```
┌──────────────────────────────────────────────┐
│ 系统提示 + 工具定义（原样，可缓存）          │  静态前缀
├──────────────────────────────────────────────┤
│ [ccx 会话状态] 状态卡               ≤ 1,200  │
│ [ccx 相关历史] 找回片段             ≤   600  │  动态部分
│ 最近窗口：最近几步，工具输出已分级  ≤ 2,000  │  默认 4,000
│ 当前用户消息 / 最新工具结果（热）   单独上限 │
└──────────────────────────────────────────────┘
```

- 状态卡和找回片段放在静态前缀之后（作为第一条合成的 user 消息，或合并进窗口里的第一条 user 消息），**不放进系统提示**，这样系统提示保持逐字节不变。
- 窗口只在**步**的边界切：一步 = 一条 assistant 消息加上它的全部工具结果。切完以后不能留下孤立的 `tool_result` 或 `tool_use`。
- 最新一步的工具结果（“热”结果）有单独的上限，默认 2,500。模型刚刚请求这份结果，必须能看到足够的内容才能往下做。

## 4. 每一步的处理流程

```
请求 → 解析（三种协议）→ 记录新增消息（复用 ctx session，加密）
     → 工具输出分级（规则，按内容哈希缓存）
     → 选窗口（从最新往回取，直到预算）
     → 状态卡（若有已完成的折叠，就用新卡）
     → 新的用户消息：在会话存档里找回相关片段
     → 组装、校验协议约束 → 上游
响应 → 记录 → 若窗口超过高水位：后台异步折叠
```

**折叠**用两道水位线控制，并且是异步的：

- 窗口加上未折叠内容超过高水位（默认 3,000）时，在响应返回之后，后台把最旧的若干步折进状态卡，直到降到低水位（默认 800）。
- 下一次请求如果折叠已经完成，就用新卡；还没完成，就暂时超预算发送（软上限），不阻塞。
- 超过硬上限（默认 `2 × budget`）时才同步等待折叠。
- 两次折叠之间，请求只在尾部追加，前面的内容逐字节不变，提示缓存可以命中。折叠时只失效一次。

## 5. 状态卡

状态卡是 ccx 的核心，相当于这次会话的工作记忆。它是 Markdown，每一条都有 id 和来源轮次：

```markdown
## 目标
- [g1] 把 payments 的对账任务迁到新队列（第 3 轮，用户原话：“……”）
## 用户要求（逐字）
- [r1] “不要动 legacy/ 目录”（第 3 轮）
- [r2] “测试必须全绿再提交”（第 7 轮）
## 已确定
- [f1] 队列配置在 config/queue.yaml；新队列名 recon-v2（第 12 步）
## 进展
- [p1] 已改 worker.rs 和 config；单测 41/43 通过（第 30 步）
## 当前 / 下一步
- [n1] 修 test_retry_backoff 的超时
## 未解决
- [e1] test_retry_backoff：timeout after 5s（第 31 步，obj_8f2）
## 资料索引
- obj_8f2 第 31 步 cargo test 输出（失败 2 项）
- obj_51a src/worker.rs 全文（412 行）
## 已结束的任务
- [t1] 修复登录页样式（第 1–2 轮，已提交 abc123）
```

**更新方式：只做增量操作，不整卡重写**。折叠时，模型拿到“当前卡 + 要折叠的几步”，返回一组操作：`add` / `update` / `remove` / `close_task`，由程序去执行。这样可以避免“摘要的摘要”一轮轮失真，也方便逐条追溯来源。

程序会检查：

- 每一节有条数上限，超出的最旧条目移入会话存档，仍然可以找回；
- “用户要求”一节的内容必须能在对应轮次的用户原话里逐字找到，找不到就拒绝这条操作；
- 整张卡不超过 1,200 token，超出时先压缩“进展”和“已结束的任务”两节。

**换话题**：用户转向新任务时，模型发出 `close_task`，旧任务压成“已结束的任务”里的一行，细节进存档。长期对话靠这个机制保持卡片大小不变。

## 6. 工具输出分级

工具输出按冷热分三级，每一级都由规则处理，结果按内容哈希缓存。同一份输出每次生成的字节都相同，提示缓存不受影响。

| 级别 | 位置 | 处理 |
|---|---|---|
| 热 | 最新一步 | 原文，超过 2,500 时按类型截取并附 id |
| 温 | 窗口内较早的步 | 按类型生成摘要（见下表）+ id |
| 冷 | 已折叠 | 只在状态卡“资料索引”里留一行 |

| 输出类型 | 温级摘要 |
|---|---|
| 读文件 | 路径、行数、符号大纲，加上模型此后引用过的行段 |
| 测试 / 构建 | 失败项及其报错、汇总行、退出码 |
| 搜索 / grep | 前 N 条匹配 + 总数 |
| 命令输出 | 开头几行 + 结尾几行 + 退出码 |
| 报错 | 原文，有上限 |
| 同一文件被读多次 | 旧的那份标成“已被第 N 步的读取取代” |
| 300 token 以下 | 原文 |

工具类型从工具名和参数识别，先覆盖 Claude Code、Codex、OpenClaw 的常用工具。识别不了的按“命令输出”处理。

## 7. 找回

模型可以通过三条路径拿回被拿掉的内容：

1. **按 id 展开**：`expand(id, range?, query?)`，支持行段和关键词过滤，不必整份返回。复用 ctx MCP 的 `expand`。
2. **按问题检索**：`recall(query)` 检索本会话存档（折叠掉的轮次、工具输出、已结束任务），复用 ctx 的混合检索。
3. **Agent 自己的工具**：重新读文件、重跑命令。摘要里写明“可重新读取”，这是最自然的兜底。

另外，每条**新的用户消息**会自动在会话存档里找回相关片段，放进“相关历史”（≤ 600）。

**交付方式**：先走 MCP，因为 Claude Code、Codex、OpenClaw 都支持，不需要改代理协议。代理自己注入工具、在内部循环执行的方案（要处理流式输出，以及 ccx 工具和 Agent 工具混在一起调用的情况）放到后面，只在 Agent 不支持 MCP 时考虑。

**自适应钉住**：同一个对象在 K 步内被找回或重新读取两次以上，就把它钉在窗口里保留 N 步，并记入日志用于调参。这是对“压得太狠导致反复找回”（见第 10 节的指标）的直接对策。

## 8. 协议约束

| 约束 | 处理 |
|---|---|
| `tool_use` / `tool_result`（Chat 的 `tool_calls` / `tool`，Responses 的 `function_call` / `function_call_output`）必须成对 | 只在步的边界切，组装完校验一遍，不通过就原样转发 |
| Anthropic 消息必须 user、assistant 交替出现，且以 user 开头 | 状态卡作为第一条 user 消息；窗口如果以 user 开头，就把状态卡合并进去 |
| 扩展思考：进行中的工具循环要回传最后一条 assistant 消息的 thinking 块 | 最新一步原样保留；较早步的 thinking 块可以去掉（要用真实网关验证） |
| Responses 的 reasoning 条目（`encrypted_content`） | 只保留最新一步的 |
| Responses 用 `previous_response_id` 的有状态请求 | 历史在服务端，ccx 无法精简，原样转发并记录 |
| 流式输出 | 只改请求，不改响应，流式原样透传 |
| Agent 自己的压缩摘要（例如 Claude Code 的 compact） | 当作普通 user 消息，正常参与折叠 |

## 9. 缓存

动态部分只有几 K，就算缓存不命中，代价也很小。100K 历史即使全部命中缓存，按约 1/10 计价也相当于约 10K；而 4K 未命中就是 4K。所以短上下文的思路本身就缓解了“改写历史会让缓存失效”这个老问题。真正值得缓存的是静态前缀，ccx 从不改它。

动态部分里，两次折叠之间只追加不改写，工具摘要按哈希缓存保证字节稳定，所以缓存仍然能命中一部分。

## 10. 运行模式、降级与指标

- `ccx.mode`：`off` / `shadow`（计算精简视图并记录，但仍转发原请求）/ `on`。可以按 Agent 单独设置。shadow 模式用来在真实轨迹上统计 token 构成，并离线回放对比。
- 降级：解析失败、校验失败、折叠失败、有状态请求，都退回原请求转发，记一条 `ccx_fallback` 日志并注明原因。
- 每一步记录：动态 token、静态 token、窗口步数、状态卡大小、找回调用次数、重读次数、折叠调用的 token 和延迟、降级原因。

## 11. 与 ctx 的关系和代码组织

用 Cargo workspace（M0 已完成）：

```
Cargo.toml        workspace；根包仍是 ctx（库 src/lib.rs + 二进制 src/main.rs）
crates/ccx/       ccx 二进制，依赖 ctx 库：协议解析（inject）、上游地址校验（proxy）、用量解析（store）
```

- 先不单独抽 `core` crate：ccx 直接依赖 ctx 库，代码不重复，合并时零成本。等 M1/M2 真正用到 session、store、embed 时，再按实际依赖面把它们抽到 `crates/core`。
- ccx 用独立的 `CCX_HOME`（默认 `~/.ccx`）和端口（7789），和 ctx 实例互不影响。
- **合并前不要把两个代理串起来**。顺序是 agent → ctx → ccx 的话，ctx 注入的记忆会被 ccx 当成历史压掉；顺序是 agent → ccx → ctx 的话，ctx 记录到的是精简后的对话，提炼质量会下降。
- 合并以后是一条流水线：原始消息先记录（供 ctx 提炼），ccx 生成精简视图，ctx 的长期记忆进入“相关历史”那一层，会话结束时状态卡作为 ctx 提炼的额外输入。

## 12. 评测

| 评测 | 用途 |
|---|---|
| **LOCA-bench**（主） | 上下文从 8K 到 256K 可控。对照组：不开 ccx、LOCA 自带的清空工具结果、ccx（预算 2K / 4K / 8K）。直接检验“短上下文更聪明”这个假设 |
| **BEAM 对话回放** | 长期对话的个人助理场景：把 BEAM 的长对话逐轮经过 ccx，在对话中途提问，对比 ccx 4K 和完整上下文。复用现有数据，成本低 |
| **PinchBench / Claw-Eval**（后） | OpenClaw 场景，和 TokenPilot 对比 |

指标：任务成功率（主）、每步动态 token 的 p50 / p95、总输入 token、找回和重读次数、折叠开销、降级率。模型统一用 gemini-3.8-flash-high；论文里的数字只作参照，不直接比较。

## 13. 里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| M0 测量 | workspace 拆分；shadow 模式；LOCA-bench 接入并跑出基线 | 有每步 token 构成报表和基线成功率 |
| M1 窗口 + 分级 | 按步切窗口、三级工具输出、id 和 MCP `expand`；不调用模型 | LOCA 动态 token p95 ≤ 预算 + 热上限；成功率不低于基线 |
| M2 状态卡 | 增量操作折叠、异步水位、用户原话校验、换话题 | 长对话中动态 token 不随轮数增长；LOCA 在长档位（≥ 64K）上的成功率超过基线 |
| M3 找回 | 会话存档检索、自适应钉住 | 重读和找回次数比 M2 低，成功率不降 |
| M4 实验 | 工具定义和系统提示瘦身；接入 ctx 长期记忆 | 单独评测，默认关闭 |

## 14. 待决问题

1. 静态前缀往往比整个动态部分还大。工具定义瘦身（只暴露相关工具）要不要进核心？它会改变 Agent 的行为，风险比较高。
2. 折叠用哪个模型：和答题同一个模型，还是更小更便宜的模型？受限于“只用一个网关、一个模型”的约束，先用同一个。
3. 用户大段粘贴（日志、代码）怎么处理：用户的文字逐字保留，粘贴进来的代码块和日志超过上限时按工具输出分级处理？
4. 默认预算定 4K 还是按任务类型自适应：先固定 4K，用 LOCA 的 2K / 4K / 8K 曲线来决定。

# ctx 架构

日期：2026-09-28。依据 [ADR 0008](adr/0008-memory-first.md)：目标是好用的长期记忆，成本不是优化目标。

## 数据流

```
Agent ──请求──▶ proxy ──▶ 上游模型
                 │  ├─ session：会话键、项目识别、本步新增消息 → 事件库（加密）
                 │  ├─ recall：规则 + 触发器 + 混合检索（仅新用户消息 / 新报错时）
                 │  └─ inject：规则进系统提示；召回结果挂在该消息上，本会话后续每步保留
                 └─ 响应：助手文本、用量 → 事件库

会话空闲 / task_end ──▶ extract：对话摘要 + 相关旧记忆 → 模型 → 新建 / 更新 / 跳过（近似去重）
                   │                                      ▼
                   │     Agent ──MCP recall/remember──▶ memory/*.md（真相源，git 记录） ◀── CLI / 面板 / SDK
                   │                                      │
                   │                                      └─ 内存索引：BM25（jieba 分词）+ 语义向量（向量缓存在 SQLite）
                   └─▶ episodes：原始对话切成片段（加密存 SQLite）+ 独立的 BM25 / 向量索引，只供显式检索
```

## 模块

| 模块 | 职责 |
| --- | --- |
| `config` | 配置；读取旧版配置时迁移核心项，实验功能保持关闭 |
| `memory` | 记忆格式（v2，约 15 个字段）、v1 文件自动迁移、触发器匹配 |
| `store` | 记忆文件与增量索引、单一 SQLite（事件、会话、召回日志、用量、向量缓存）、git 提交、维护批次回滚 |
| `embed` | 本地语义模型（fastembed / ONNX Runtime，CPU），懒加载，失败时退回关键词检索 |
| `index` | 分词（英文词干 + jieba 中文分词）、BM25 覆盖度得分、向量相似度 |
| `recall` | 唯一召回入口，代理、MCP、CLI、API、评测共用；`inject` / `search` 两种模式 |
| `episode` | 原始对话片段（episodic 层）的切分与索引 |
| `session` | 会话键、项目识别、本步新增消息（对话记录）、每会话已注入记忆 |
| `inject` | 三种协议的读写、步骤特征、渲染与注入 |
| `extract` + `llm` | 会话结束后提炼记忆；共享的模型调用与每日调用上限 |
| `proxy` / `api` / `server` | Agent 代理、本地 REST 与面板、守护进程与后台任务 |
| `integrations/`（仓库目录，非 Rust 模块） | Hermes 记忆插件（Python）与 OpenClaw 记忆插件（JS），通过 REST 接入，替代代理 |
| `mcp`、`adapters`、`observer`、`feedback`、`consolidation` | MCP 服务、Agent 启动包装、工具结果解析、漏召回修复、维护 |
| `experimental/` | Gate、本地分类器、ActionGuard、上下文驱逐；默认关闭 |

## 关键设计

**记忆格式。** `id, type, title, scope, status, source, pinned, confidence, triggers, expires, supersedes, superseded_by, evidence, created_at, updated_at` + Markdown 正文。`source` 为 `user`（你说的）、`agent`（Agent 或提炼器推断）或 `observed`。只有 `source: user` 的规则会生效。v1 文件（`card`、`tier`、`created_by`、触发器匹配 DSL 等）在读取时转换并提交一次 git。

**召回。** 始终生效的规则和 pinned 记忆先取出；触发器匹配当前步骤的用户文本、工具名、错误签名或触及的文件；然后是混合检索：语义相似度 ≥ `min_similarity`，或关键词覆盖度 ≥ `min_keyword`，得分为 0.75×语义 + 0.25×关键词，并丢弃低于最高分 80% 的结果。关键词覆盖度是“查询信息量（IDF）中被该记忆覆盖的比例”，查询里记忆库没有的词计入分母，因此单个偶然重合的词不会触发召回。候选只从当前项目可见的记忆中取（其他项目的记忆不会把本项目的挤出候选池）；但“最高分”取全库最高，所以当问题明显更像另一个项目的记忆时，本项目的弱匹配不会被注入。

**两种召回模式。** 上面是代理自动注入用的 `inject` 模式：宁缺毋滥。Agent 或人主动提问（MCP `recall`、`ctx recall`、`GET /api/v1/recall`，默认 `mode=search`）用 `search` 模式：按相关度返回前 `limit` 条（最多 50），语义下限 `search_min_similarity`（0.25），不做相对截断，并把最多 `search_episodes`（5）条原始对话片段与记忆按同一得分混排。实验里用 RRF 融合替代线性加权，B1 recall@3 从 0.942 降到 0.848，未采用。

**原始对话片段（episodic 层）。** 提炼会丢细节（金额、顺带提到的名字、助手给过的推荐）。会话提炼时，同时把用户与助手的原话按轮切成约 1200 字的片段（长回复分段，并重复用户提问的开头；工具输出不入库），加密存入 SQLite，建立独立索引并计算向量。只有 `search` 模式会检索它们，结果 `channel: episode`、`type: episode`；同一轮对话的多个片段只返回一个（否则同一句话会重复出现，放大过时的数值）。`ctx reindex` 会为之前的会话补建片段。

**对话轮次与用户原话。** 一轮 = 一条用户消息加随后的回复。加载时按会话写入顺序（`sessions` 的 rowid）和片段序号（`seq`）把片段归并成轮，在同一范围（项目）内连续编号；编号在重启后不变，新会话接着编号。每条用户消息单独建一个文档（`tu_…`，关键词加向量，向量存在 `vectors` 表，缺失的由 `ensure_vectors` 补齐）。检索结果带 `turn`：片段取它所在的轮，记忆取它出处那一轮（它所在会话里最相似的片段）。轮次号越大越新，同一天说的两件事也能分出先后（BEAM 每个批次约 50 条消息只有一个日期，知识更新题的新旧两个值全部在同一天）。`turns=true` 时，检索结果附上一段用户原话记录 `type: turnlog`：问总结、先后顺序、次数的题给出这个范围内的全部用户消息（按轮次排列，超过预算时按相关度取舍），其他题给最相关的 20 条。

**助手回复的提纲与要点。** 每一轮还带一句助手回复的概要：默认是不用模型、从回复原文取出的提纲（第一句话，加上小标题和加粗的要点，例如“配置匿名化；引入人工把关；先做试点”）；打开 `extraction.turn_notes` 时，由提炼模型为每一轮写一到三句要点（存在 `turn_notes` 表，优先于提纲）。概要不进检索索引（索引里只有用户消息：概要会让助手讨论过某话题的轮次排到用户自己陈述的轮次前面）；在用户原话记录里，只有问总结和“你当时怎么建议的”这类题才显示（“→ Assistant: …”）——其他题里，它会被当成用户自己做的事或说的值（助手建议的 ESLint 规则被当成用户启用的，助手提到的“通常 6–9 个月”被当成用户最新的说法）。`turn_notes` 默认关闭：在 BEAM 100K 上，让提炼模型顺带写要点使事实类记忆少了约 5%，矛盾消解和知识更新的损失大于总结的收益；提纲不花 token，能拿到大约一半的总结收益。

**事件日期与版本链。** 每条记忆有两个日期：`observed_at`（什么时候说的）和 `event_at`（事情什么时候发生，提炼时从会话日期换算成绝对日期，允许只到月或年）。事实变化时，提炼器返回 `supersede`：新建一条当前状态的记忆（`supersedes` 指向旧的），旧的标为 `superseded`，不再被召回，但作为 `history` 附在新记忆的检索结果上（API `history`、MCP `previously`）。`update` 只用于给仍然成立的记忆补充细节。

**矛盾。** 用户前后说了不能同时成立、又没有说明变化的话（“做过 5 道抛硬币题”与“从没做过抛硬币题”）时，两条都保留，标为 `contested`，用 `conflicts_with` 互相关联；检索结果带上 `conflicts`（MCP `conflicts_with`），让答题方指出矛盾而不是只选一边。识别方式：每个会话提炼后，新记忆中带否定说法（从未、没有、never、haven't 等）的与相似记忆配对，一次小的模型调用判断哪几对矛盾；“从未”说在前、后来做了算进展。开关 `extraction.contradictions`，默认开启，只在有候选对的会话多一次调用。同一次调用也判断“更新”：两条很相似、只是数值不同的记忆（“杂货预算 500”与后来的“提高到 550”），判为更新时旧的标为被取代。提炼模型把“后说的从未做过”当成更新时，按矛盾处理（否定句不会取代肯定句）。检索时，一对未解决的矛盾合并成一条 `type: conflict` 的提示放在最前面（两句话、各自的日期、“用户没有说哪句是对的”），不再作为两条普通记忆出现。只有问“是否做过、是不是这样”的题（“Have I…”“Did I…”“我有没有…”）才给出矛盾提示和 `conflicts`；问次数、日期、总结的题，两句话都只是证据（否则回答会被带偏，BEAM 上曾有约 30 道非矛盾题因此答错）。

**提及顺序与提及次数。** 问“按提起的先后”时，检索结果按轮次排列（没有轮次时按创建顺序）；时间类问题按事件日期排，同一天内按轮次。检索结果带 `mentioned`（该记忆是本范围内第几条被提到的）。用户在后面的会话里再次提到同一件事时不重复存储，而是在原记忆上记一次（`mentioned_at`，每个会话最多一次；提炼动作 `mention`，或被判为重复时自动记录），用于“我提过几次”。

**被取代的记忆。** 默认不召回，只作为 `history` 附在新版本上；时间类问题（“原计划哪天”“之前是多少”）会把它们也放进候选（分数打九折，`status: superseded`）。

**会话时间线。** 提炼时模型同时返回 `session_summary`（两三句：用户谈了什么、助手给了什么），存为 `type: summary` 的记忆，每个会话一条。它们不参与普通检索；总结、提及顺序、计数类问题时，按会话顺序拼成一条 `type: timeline` 放在前面，最多占预算的 35%，会话太多时只保留与问题最相关的若干行（仍按顺序）。

**长期指令。** `type: instruction`：用户对助手回答方式的长期要求（“讲依赖事件的概率时一定画树状图”）。`search` 模式每次把本范围的长期指令全部放在最前面（最多 10 条，按相关度排序；`channel: instruction`），不受相关度下限限制：一个人的长期指令不多（BEAM 每段对话约 4 条），漏掉一条就答不对。

**实体通道。** 问题里点到名字的人、地点、产品，其相关记忆即使正文没有出现这个名字也能被找到；但只因名字被召回的记忆排在文本匹配之后，每次最多 `limit/4` 条（至少 3 条）。

**简报模式（可选，`brief=true`）。** 先宽松取回约 12,000 token 的材料（50 条候选、12 段原始片段），加上用户原话记录（总结、顺序、次数类问题给全部用户消息，最多约 16,000 token；其他问题给最相关的 20 条），再用一次模型调用写成针对问题的简报：相关事实按轮次排列、算好的次数和日期差、变化过的当前值（取轮次最大的说法）、矛盾（只在问“是否”时）、适用的长期指令和偏好；材料里只有话题、没有问的那个细节时，明确写“记忆中没有关于……的信息”（点名某人的建议，必须是那个人说的，不能拿助手的建议充数）。简报第一行 “Answer:” 里的天数由程序按日历核对（模型常算错，例如把 7 月 10 日到 9 月 12 日算成 67 天）。`dry_run=true` 只返回简报的材料、不调用模型，用于检查检索。结果以一条 `type: brief` 开头（最多占 `budget` 的 40%，不超过 800 token；问总结和“你当时怎么建议的”这类题不超过 2,000 token，否则各阶段的细节写不进去），后面是按剩余预算打包的原始检索结果（简报可能漏掉细节）。代价是每次检索多一次模型调用；调用失败时退回普通检索结果。

**话题摘要（整合）。** 提炼时每条记忆带 1–3 个话题标签，第一个总是类别（任何工作坊都是 `workshops`）。同一作用域、同一话题的活跃记忆达到 3 条时，生成一条 `type: digest` 的摘要，按时间列出全部成员，总长约 3,200 字（成员越多每行越短，90–200 字；超过约 35 条才舍去最早的）。不调用模型，确定性生成，内容不变不重写；`ctx reindex` 会全部重建。摘要只供 `search` 模式检索，用于“一共花了多少”“去过哪些”这类需要整类信息的问题；不参与自动注入。

**线索触发（编码）。** 编码提炼提示词为每条记忆给出最多 3 个线索：文件路径或 glob（`file`）、报错文本（`error`）、特征命令（存为 `keyword`，匹配用户文本和工具参数）。只保留在本次会话原文中出现过的线索，过于常见的命令（`git`、`npm`、`pytest` 等）被丢弃。相对路径的文件线索也匹配任意目录下的同一路径。代理在每个新步骤（包括工具调用）上检查线索，命中的记忆挂在最新的用户或工具消息上。

**深度检索（多步）。** `search` 模式加 `deep=true`（REST）或 `deep: true`（MCP）时，先用一次模型调用把问题拆成 1–3 个子查询，并给出答案所在的日期窗口；每个子查询取较宽的候选集，窗口内的结果加分，先保留每个子查询的最佳结果（覆盖问题的每一部分），再按分数补齐。普通检索不调用模型。

**偏好。** 通用提炼把用户的口味和要求记为 `type: preference`：从要求、选择、称赞和拒绝中归纳出可用于以后推荐的通用陈述，保留全部条件。检索结果和插件注入会标注为用户偏好。

**同一事件不重复记录。** 提炼前按每条用户消息分别检索相关旧记忆（最多 30 条）交给模型；提示词要求再次提到的过去事件不重复记录。程序兜底：内容几乎相同（向量相似度 ≥ 0.92）且事件日期相差不超过 7 天的两条视为同一事件（“上周六”在不同会话中换算出不同日期）；比较数字时忽略日期。

**检索结果打包。** `search` 模式可带 `budget`（REST），按读者的 token 预算打包：事实、偏好、话题摘要先放；原始片段排在后面，至少保留 35% 预算，每段只保留用户那一句和与问题最相关的约 400 字；放不下的条目跳过而不是截断整个列表。问题措辞里有“多少、一共、哪些、几次”时，话题摘要加分并多取候选；有“最近、第一次、多久”时，按事件日期排列。话题和实体标签也写入关键词索引。

**可选：反思与已知实体（默认关闭）。** `extraction.reflection`：话题记忆数跨过 5、10、20…时，用一次模型调用整合出偏好、当前状态和去重后的次数与总额（每个会话最多一次，最多 5 个话题）。`extraction.known_entities`：提炼时给模型最常见的 20 个已知实体和一句上下文，用于把“我妹妹”补成名字。二者在 LongMemEval 开发集上都没有测出收益，分别增加约 32% 和 20% 的提炼 token；反思还会在两个阈值之间过时（例如写着“参观过 4 座博物馆”，之后又去了 2 座）。代码保留，留待更难的测评再试。实体标签只保留在会话原文、已知实体或相关记忆中出现过的名字。

**实体索引。** 提炼时记录每条记忆涉及的人名、地名、组织、产品。`search` 模式下，问题中按整词提到的实体会把所有带该实体的记忆拉进候选（即使正文写的是“用户的妹妹”）；自动注入不用实体通道。

**按话题、按时间排列。** `search` 模式的结果按向量相似度（≥ 0.75，事先依据“同类不同事件相似度 0.76–0.79”确定）贪心聚成话题：话题按相关度排序，话题内按时间从早到晚排列，并带 `group` 编号和日期，读者能看出一个事实如何变化、哪个值最新。只影响顺序，不增删结果。

**注入时机。** 只在新的用户消息或新的报错时检索，工具输出不当作查询。召回结果挂在触发它的那条消息上（锚点），只要这条消息不变，后续每步都会重新附上；同一会话不会重复注入同一条记忆。没有规则、没有锚点时，请求原样转发。

**写入。** 会话在空闲 `idle_minutes` 后，或 `task_end` / `session_end` 事件（带 session_id）后进入提炼。输入是脱敏后的对话摘要（用户消息全部保留，中间的工具输出优先裁剪，最多 3 万字）和召回到的相关旧记忆。提示词有两套：编码 Agent 用 `prompts/extract-v1.txt`（项目知识、教训、做法）；`extraction.general_agents`（默认 Hermes）用 `prompts/extract-general.txt`（关于用户的原子事实和事件，即 LongMemEval 上验证的版本）。模型返回 create / update（每个会话最多采用 40 条；提示词要求“一条记忆只记一个事实或事件”，保留数字、名称和绝对日期）；提炼器拒绝改写你写的记忆，丢弃无法用用户原话证实的偏好，并把证实的偏好存为 `fact`（不会自动成为规则），语义相似度 ≥ 0.88 且数字相同的新记忆视为重复（“有 3 只猫”和“有 4 只猫”向量相似度 0.92，但是不同的事实）。

**存储。** 事件只保存每步新增的消息和响应文本（AES-GCM 加密），`debug_capture` 开启时才保存完整请求。会话表保存游标，守护进程重启后不会把旧消息再记一遍。向量按记忆文本哈希缓存，文本不变就不重算。

**维护。** 过期（`expires`）归档、完全重复的记忆标记为被取代、有足够负反馈的触发器停用；按批次执行，可回滚。不会因为“长期未用”而归档记忆。

## 实验功能（默认关闭）

`experimental.gate_enabled`（LLM 判断是否需要检索；远程网关延后一步生效）、`action_guard`（`advisory` / `recheck`，在工具调用前检查带 `before_action` 触发器的教训）、`eviction_enabled`（把旧的大块工具输出替换为可展开的占位符；会使提示缓存失效）、`maintenance_enabled`（定时维护）。它们保留用于实验，不在核心路径上，也不是验收项。

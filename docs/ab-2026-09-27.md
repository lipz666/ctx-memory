严格任务成功率为 ctx 3/3、直连 2/3；若只看最终代码是否通过验证器，则两边都是 3/3。直连支付对账的进程在 260 秒时被实验外层超时终止，尽管代码已通过验证，因此不能将其缺失用量当成零，也不能据此宣称成功率改善。

两臂都正常成功的两项合计：ctx 输入 1,400,754、输出 4,865、缓存读取 963,467 token；直连输入 1,152,304、输出 4,254、缓存读取 919,883 token。ctx 输入**高 21.6%**，输出高 14.4%，缓存命中率为 68.8% 对 79.8%。这个小样本没有显示 token 节省，更不支持每成功任务成本下降 20%。网关未提供经核实的实际模型单价，按用户要求只报告 token；响应实际模型为 `gemini-3.8-flash`。

结果受模型随机性、网关波动、任务顺序和单次样本影响。此前 `clamp` 单任务流程试跑的方向与本次相反，进一步说明不可从一次任务推断收益。正式 v0.1 退出标准仍未通过。下一轮需记录实际驱逐次数和编译变化，增加重复配对及长工具输出任务；保留所有失败、超时与缺失用量，不选择性剔除。

## 支付对账重复配对

将超时上限提高到 360 秒后，重复同一起点和提示。ctx 臂通过验证，用时 300.4 秒、输入 1,425,506、输出 5,824、缓存读取 1,209,214 token；直连臂正常退出但验证失败，用时 364.9 秒、输入 1,187,139、输出 1,901、缓存读取 936,501 token。ctx 的 28 个代理步骤中，**修改请求 0 次、驱逐工具结果 0 次**。因此这次结果只能说明模型运行的路径不同，不能归因于编译或驱逐带来收益；重复试验也未提供一对都成功的成本样本。聚合结果见 [重复配对 JSON](openclaw-ab-ledger-repeat-2026-09-27.json)。

这使下一轮的诊断重点明确：先用长工具历史任务确认默认阈值何时触发驱逐，再做足量重复配对。不能为展示节省而事后挑选成功样本或调低阈值并把它说成默认配置的结果。
